# qa-planner 크리틱 rubric v2 (POST 모드 — 3축)

- **rubric_version**: `v2`
- **쓰는 곳**: `planner-critic`이 POST 런의 초안 문서(기능정의서 delta·정책정의서 delta)를 채점할 때.
- **재현성 규칙**: 자유 서술 판정 금지. 0~5 고정 척도 anchor로만 점수를 매기고, 점수마다 근거(문서 위치 인용 — 코드정합성은 코드 위치 포함)를 남긴다. 점수·근거·rubric_version은 loop-audit-log에 기록한다.

---

## 0. 크리틱 독립성 (전제)

- 크리틱은 저자(planner-lead)와 분리된 별도 에이전트다. 자기평가 금지.
- 적대적으로 동작한다 — "통과시킬 이유"가 아니라 "떨어뜨릴 결함"을 먼저 찾는다.
- 문서를 수정하지 않는다(report-only). 점수 + 근거 + 미달 축만 반환.

---

## 1. 채점 대상 3축

| 축 | 뜻 | 왜 크리틱인가(결정론 불가 이유) |
|---|---|---|
| 정합성 | 저술 대상 문서끼리·baseline과 뜻이 안 어긋남 | 용어 뉘앙스·논리 흐름 모순은 서술 판단 필요 |
| 명료성 | 검토자(비개발자)가 쉬운 말로 바로 이해 | 이해도 판정은 서술 판단 필요 |
| **코드정합성** | 문서 서술이 **실제 구현(코드)** 과 일치 | 코드 동작 의미 해석·문서 서술과의 대조는 서술 판단 필요. 결정론 게이트는 id 참조 무결성만 본다 |

> 완전성·추적성·ISO 커버리지·N/A 사유·cross-doc 값 모순·FR 연결성(frs[])은 결정론 게이트(`scripts/deterministic-gate.py`)가 판정한다.

## 2. 0~5 고정 척도 (공통 anchor)

| 점수 | 뜻 | 통과 |
|---|---|---|
| 0 | 치명 결함 | X |
| 1 | 중대 결함 다수 | X |
| 2 | 중대 미흡 | X |
| 3 | 지적 다수(경계) | X |
| 4 | 경미 지적만 (통과 가능) | O |
| 5 | 문제 없음 | O |

**PASS 조건: 정합성·명료성·코드정합성 세 축 모두 ≥ 4점.** 한 축이라도 3점 이하면 크리틱 게이트 FAIL → 해당 축이 미달 축으로 반환.

## 3. 축별 anchor

### 3-1. 정합성

**정량 기준**: `직접 모순` = 값·상태가 반대로 서술된 건. `용어 불일치` = 같은 개념을 문서마다 다른 이름으로 쓴 건. 건수는 저술 대상 문서 전체(기능정의서 delta·정책정의서 delta) 합산.

| 점수 | anchor (건수 기준) | 통과 |
|---|---|---|
| 0 | **직접 모순 1건 이상** | X |
| 1 | 직접 모순은 없으나 baseline과 논리 상충 1건 이상 + 용어 불일치 3건 이상 | X |
| 2 | 용어 불일치 **3건 이상**(직접 모순·논리 상충은 없음) | X |
| 3 | 용어 불일치 **1~2건** 또는 논리 흐름이 한 곳 모호 | X |
| 4 | **경미한 표기 흔들림만**(대소문자·띄어쓰기), 뜻은 일관. 불일치 0건 | O |
| 5 | 저술 대상 문서·baseline 완전 정합. 표기 흔들림도 0 | O |

채점 시 확인: 같은 개념이 문서마다 같은 용어인가 / 정책이 FR의 상태 전이와 논리적으로 맞물리는가 / baseline과 모순되는 서술을 `[충돌]` 마커 없이 단정하지 않았는가(마커 있으면 결함 아님).

### 3-2. 명료성

**정량 기준**: `기술 토큰 노출` = 비개발자가 못 읽는 영문 약어·내부 코드·기술 용어를 쉬운 말 병기 없이 그대로 쓴 건(예외: 시스템 키·정확 좌표·FR/P id·커밋 해시 등 근거 좌표는 제외). 건수는 문서 전체 합산.

| 점수 | anchor (건수 기준) | 통과 |
|---|---|---|
| 0 | 검토자가 **이해 불가**(문장 구조 붕괴·의미 파악 불가) | X |
| 1 | 기술 토큰 노출 **6건 이상** 또는 **문단 3개 이상**이 수동태·이중부정으로 난독 | X |
| 2 | 기술 토큰 노출 **3~5건** | X |
| 3 | 기술 토큰 노출 **1~2건** 또는 손봐야 할 문장 3건 이상 | X |
| 4 | **손봐야 할 문장 1~2건**만, 기술 토큰 노출 0. 대체로 쉬운 말 | O |
| 5 | 쉬운언어 완전 준수. 비개발자 즉시 이해 | O |

### 3-3. 코드정합성 (POST 전용)

**정량 기준**: `구현 불일치` = 문서가 서술한 동작·상태·조건·권한이 헤더 `[CODE]`(레포+커밋 범위)의 실제 구현과 다른 건. `근거 미확인` = 문서가 단정한 서술인데 코드에서 해당 구현을 찾을 수 없는 건. **`[충돌]` 마커로 드러낸 구현≠요구 항목은 결함 아님(드러낸 것)** — 마커 없이 요구사항 쪽을 사실처럼 쓴 것만 결함이다.

| 점수 | anchor (건수 기준) | 통과 |
|---|---|---|
| 0 | **구현 불일치 2건 이상** — 문서가 코드와 반대로 서술 | X |
| 1 | 구현 불일치 1건 + 근거 미확인 2건 이상 | X |
| 2 | 구현 불일치 **1건**(마커 없음) | X |
| 3 | 구현 불일치 0건, 근거 미확인 **2건 이상** | X |
| 4 | 근거 미확인 **1건 이하**, 구현 불일치 0건 | O |
| 5 | 표본 대조 전건 코드와 일치. 근거 미확인 0건 | O |

채점 시 확인:
- 문서의 상태 전이·권한 게이트·경계 조건이 실제 코드(엔티티·서비스·권한 어노테이션·화면 템플릿)와 일치하는가 — **delta 항목당 최소 1개 코드 좌표를 실제로 열어 대조**한다(전건 열람이 과대하면 delta 기준 표본 ≥50% + 마커 있는 건 전수).
- 근거 컬럼의 커밋·설계 문서 좌표가 실재하는가(dangling 근거 = 근거 미확인).
- 코드 접근 불가(레포 부재·커밋 범위 해석 불가) 시 **점수를 매기지 않고 채점 불가로 보고**한다 — 추정 점수 금지.

## 4. 크리틱 반환 양식

```json
{
  "rubric_version": "v2",
  "critic_agent": "planner-critic",
  "scores": {
    "정합성": {"score": 4, "evidence": "기능정의서 delta FR-APP-146 ↔ 정책정의서 P-APP-021 용어 일치, 경미 표기 흔들림 1건"},
    "명료성": {"score": 5, "evidence": "기술 토큰 노출 0, 쉬운언어 준수"},
    "코드정합성": {"score": 3, "evidence": "FR-APP-147 '강제 로그아웃 후 안내 표시' 근거 커밋을 코드에서 미확인 2건"}
  },
  "pass": false,
  "failed_axes": ["코드정합성"]
}
```

- `pass = 세 축 모두 score >= 4`.
- `evidence`는 반드시 위치 인용 — 코드정합성은 **문서 위치 + 코드 위치(파일 경로 또는 커밋)** 병기. 위치 없는 근거는 무효.
