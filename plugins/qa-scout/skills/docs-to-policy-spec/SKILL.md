# docs-to-policy-spec (v1.0)

기능정의서에서 **정책정의서 draft**를 파생하는 스킬.

## 왜 파생인가

기능정의서 §1 각 FR의 "상세 정책 / 기능 설명" 컬럼은 이미 정책성 규칙(가드·검증·상태 전이·권한 게이트·데이터 무결성·보안·부수 효과)을 블록으로 담고 있다. 정책정의서는 이 규칙들을 **기능 단위가 아니라 정책 단위로 재조직**한 것이다. 그래서 기능정의서가 SoT이면 정책정의서는 그 파생물이고, 관련 FR 연결이 자동으로 따라온다.

## 사용 시점

- scout가 `docs-to-function-spec`로 기능정의서를 완성한 **직후** 호출.
- 입력 기능정의서가 없으면 중단(파생 소스 부재). scout가 기능정의서 stub(외부 양식 대체)만 있으면 그 외부 양식(시트/CSV) 위치를 입력으로 받는다.

## 입력

| 항목 | 형태 | 필수 |
|---|---|---|
| 기능정의서 | `feature-spec.md`(§1) 또는 `기능정의서_master.csv`(상세 정책 컬럼) | 필수 |
| 정책 대역 config | yaml (`policy-band-config.example.yaml` 복사·채움) | 필수 |
| baseline 정책 마스터 | `정책정의서_master.csv` (재사용 ID 회피용) | 선택(없으면 빈 baseline) |

config에서 읽는 것: `id_prefix`·`fr_prefix`·`bands[]`(도메인↔대역↔FR 대역↔탭)·`baseline_master`. **프로젝트 상수는 전부 config에만** — 스킬 본문·스크립트에 프로젝트명 하드코딩 금지(변수형, CTMS 등 재사용).

## 출력

`{프로젝트 문서 원본}/정책정의서/drafts/정책정의서_{도메인}_초안.md` — **11컬럼 delta 양식**:

```
변경 유형 | 정책 ID | 정책 구분 | 정책명 | 정책 목표 | 정책 내용 및 기준 | 적용 범위 | 관련 FR | 비고 | 근거 | 마커
```

- 가운데 8컬럼(`정책 ID ~ 비고`)이 마스터(`정책정의서_master.csv`) 8컬럼과 **문자열 1:1 일치** — 승인 시 그대로 마스터로 옮겨진다.
- 앞뒤 3컬럼(`변경 유형`·`근거`·`마커`)은 검토용 delta 메타. 최초 구축은 전부 `추가`.
- **draft까지만** — 마스터 CSV 직접 수정 금지(사람이 승인 행만 반영, GxP no-auto-apply).

## 파생 절차

### 1. 기능정의서 흡수
각 FR의 상세 정책 블록(`[핵심 동작]`·`[입력 규칙]`·`[거부 처리]`·`[기록]` 또는 8단 정형 `핵심 룰·경계 조건·상태 전이·권한 게이트·데이터 무결성·화면 동작·부수 효과·참조` — 프로젝트 양식 무관)을 읽어 **정책성 규칙 문장**을 뽑는다. 정책성 규칙 = "무엇을 강제/차단/허용/기록하는가"의 판단 기준이 있는 문장.

### 2. 정책 단위 분해 (한 행 = 정책 하나)
- 정책 3요소를 모두 채울 수 있어야 한 행이 된다 — **목표**(정책 목표: 왜) / **대상**(적용 범위: 어디에) / **수단**(정책 내용 및 기준: 어떻게).
- 하나의 FR이 여러 정책을 담으면 여러 행으로 쪼갠다(예: 로그인 FR → 계정 잠금·로그인 허용 조건·실패 안내 최소 노출 각각 1행).
- **여러 FR에 공통으로 걸린 규칙은 정책 1건으로 병합**하고 `관련 FR`에 다중 참조(예: `FR-001, FR-004`).

### 3. 8컬럼 채움
- `정책 구분` = config `bands[].policy_category` (FR 도메인으로 대역 판정).
- `정책명` = 규칙의 한 줄 이름(쉬운 말, 명사구).
- `정책 목표`·`적용 범위`·`정책 내용 및 기준` = 3요소.
- `관련 FR` = 근거 FR id만(config `fr_prefix` 검증. 새 id 발급 금지, 기능정의서에 실재하는 id만).
- `비고` = 도메인 경계·재배치 후보·주의. 정책 판단이 갈리는 지점은 `[충돌]`/`[미확정]` 마커(§5).

### 4. 정책 ID 대역 발급
- FR 도메인 → config `bands[]`에서 대역 결정 → 그 대역 안에서 baseline max+1 발급(`{id_prefix}{NNN}`).
- baseline·선점 delta에 이미 쓰인 번호는 건너뛴다(재사용 금지). 선점 ID는 draft 머리말에 명시.

### 5. 무망상 가드 (위반 시 파생 실패)
- **기능정의서에 근거 없는 정책은 만들지 않는다.** 상세 정책 블록에서 문장을 못 짚으면 그 정책은 생성 X.
- 코드·보안 설정에서만 드러나고 기능정의서에 안 실린 규칙(예: CSRF·클릭재킹·fail-closed 같은 방어 설정)은 **`[원본필요]` 마커로 후보만 비고에 남기고 본문 행 생성 금지**. 이는 planner POST(코드가 진실) 또는 원본 보강 트랙의 몫 — 스킬 범위 밖.
- 추정 채움 금지([[bridge-wrapping-pattern]]). 값이 비면 `[자료 부족] (무엇 — 확인한 입력)`.

### 6. 마커 (기능정의서 마커 승계)
- `[충돌]` — 기능정의서 상세정책/비고에 구현≠요구가 드러난 정책은 그 마커·근거를 승계해 비고에 병기(자동 해소 금지 — 사람 판단).
- `[미확정]` — 파생 근거는 있으나 정책 경계가 모호.
- `[원본필요]` — 기능정의서만으론 파생 불가, 코드/원본에서만 확인되는 규칙(§5).

### 7. 쉬운 언어
독자는 비개발자. 기술 용어는 쉬운 말로 바꾸거나 첫 등장에 괄호 병기. 시스템 키·정확 경로·정책값 인용은 예외. 기능정의서 문체(블록·능동태) 준수.

## 자가 검증 (발행 전)

`plugins/qa-scout-kit/scripts/policy-spec/validate-policy-spec.py`로 결정론 검증. exit 0 아니면 발행 FAIL:

```
python plugins/qa-scout-kit/scripts/policy-spec/validate-policy-spec.py \
  --draft <정책 draft.md> --config <policy-band-config.yaml> \
  --funcspec <feature-spec.md 또는 기능정의서_master.csv>
```

검사 항목:
1. 8 핵심 컬럼 헤더가 마스터 헤더와 1:1 일치
2. 모든 `관련 FR` id가 기능정의서에 실재(유령 0). 단 `관련 FR` 빈 행은 비고에 사유 필수
3. 정책 ID가 config 대역 준수(도메인↔대역 정렬) + 중복 0
4. 3요소(정책 목표·적용 범위·정책 내용 및 기준) 빈 셀 0 (또는 `[자료 부족]` 마커)
5. `[원본필요]` 마커 행은 본문 정책 행으로 세지 않음(후보 격리 확인)

## scout·planner 연계

- **scout 배선**: scout가 기능정의서 완료 후 본 스킬 호출 → 도메인별 draft 생성 → 정제 완료 보고에 정책 draft 건수 포함.
- **planner 연계**: draft의 승인 행이 사람 검토를 거쳐 `정책정의서_master.csv`가 되고, 이 마스터가 planner POST 모드의 읽기 전용 baseline이다. planner는 이후 코드 변경분을 11컬럼 delta로 얹는다(같은 양식이라 이음매 없음).

## 금지
- 마스터 CSV 자동 반영(draft까지만, GxP no-auto-apply)
- 기능정의서 근거 없는 정책 생성(추정 금지)
- 프로젝트 상수 하드코딩(변수형 — config에만)
- `[충돌]` 자동 해소, 구글시트 미러 재생성(markdown-to-sheets 몫)
- 이모지, 감정 표현
